> **목적:** 아이디어를 많이 내는 것보다, 공모전의 네 가지 필수 평가 항목에 맞는 아이디어를 만들고 비교하기 위한 팀 작업 문서  
> **주의:** 주최 측은 세부 배점을 공개하지 않았다. 아래의 점수표와 선별 기준은 팀 내부 의사결정용이며 공식 배점이 아니다.

현재 검토 중인 아이디어와 기술 타당성은 [IDEA_CANDIDATES.md](IDEA_CANDIDATES.md)에 정리한다.
선정 아이디어의 공식 제안서 작성 순서와 항목별 초안은 [PROPOSAL_PLAN.md](PROPOSAL_PLAN.md)에 정리한다.

## 0. 먼저 기억할 한 문장

좋은 출품작은 **명확한 탑승자/운전자의 반복되는 문제를, 주행·정차 맥락과 차량 데이터·기능을 이용해, 스마트폰보다 자연스럽고 안전하게 해결하며, 다시 쓸 이유와 실제 구현 증거가 있는 앱**이다.

아이디어를 아래 문장으로 설명할 수 있어야 한다.

> `[구체적인 타깃]`이 `[구체적인 이동 상황]`에서 겪는 `[반복적이고 중요한 문제]`를, `[차량 데이터/기능 및 Pleos SDK]`로 감지·판단·실행하여 `[측정 가능한 결과]`를 만든다. 스마트폰만으로는 `[차량만의 정보/제어/맥락]`이 없어 같은 경험을 제공하기 어렵다.

## 1. 공식 평가 기준

1차 서류심사는 다음 네 항목을 필수로 평가한다. **항목별 세부 배점은 공개되지 않았다.**

| 공식 평가 항목 | 주최 측이 밝힌 평가 관점 | 아이디어 단계의 핵심 질문 |
|---|---|---|
| 차량특화성 | 모바일 대비 차량 환경만의 독자적인 가치와 우위가 있는가? 주행·정차 맥락 및 차량 기능과 유기적으로 결합되는가? | 이 앱을 스마트폰에 그대로 옮기면 가치가 크게 떨어지는가? |
| 창의성 | 기존에 없던 독창적·혁신적 아이디어인가? 운전자·동승자의 Pain Point와 Needs 및 해결 방식이 명확한가? | 누구의 어떤 순간이 불편한지 장면으로 설명할 수 있는가? 해결 구조에 새로운 결합이 있는가? |
| 기술 활용성 | Pleos Playground의 SDK·API를 핵심 기능과 사용 경험에 적절히 활용하는가? | SDK가 빠지면 핵심 경험 자체가 성립하지 않는가? |
| 사업성 | 타깃 고객이 명확하고, 사용자 확보와 지속 이용·확대 가능성이 있는가? 타깃 분석, 예상 MAU, Retention Rate, 향후 확대 계획 등이 있는가? | 첫 유입 경로, 반복 사용 계기, 다음 확장 시장을 숫자와 가정으로 설명할 수 있는가? |

### 개발 산출물 가산점

- 프로토타입 시연 영상(목업·화면 녹화 포함)과 GitHub 저장소(소스 코드 및 APK 포함)는 선택 제출물이다.
- 1차 접수 때 개발 산출물을 함께 제출하면 제출 수준에 따라 단계별 가산점이 부여된다.
- 2차 PT 대상 팀은 PT 전까지 실제 동작하는 앱을 완성해야 한다.
- 1차에 낸 산출물은 2차 PT 전까지 고도화할 수 있다.
- 2차 PT의 세부 심사 기준은 2026-10-28 현재 추후 공지 예정이다.

따라서 **기획만 좋은 아이디어보다, 핵심 차량 연동 장면 한 가지를 안정적으로 시연할 수 있는 아이디어가 전략적으로 유리하다.** 이 문장은 공개된 가산점·시연 규정을 바탕으로 한 팀의 해석이며 별도의 공식 평가 항목은 아니다.

## 2. 평가 항목을 아이디어 언어로 해석하기

### 2.1 차량특화성

강한 아이디어의 증거:

- 출발 전, 주행 중, 정차, 충전·주유, 주차, 도착처럼 **차량 이용 단계**에 따라 동작이 달라진다.
- 차량 상태, 경로, 위치, 좌석·공조·도어 등의 정보가 문제 해결의 원인이거나 실행 수단이다.
- 사용자가 매번 앱을 열지 않아도 차량 상태 변화가 적절한 행동을 촉발한다.
- 운전자뿐 아니라 동승자·어린이·가족·반려동물·상업 운전자 등 차량 안의 역할 차이를 반영한다.
- 운전 중에는 짧고 안전한 상호작용, 정차 중에는 자세한 설정으로 경험을 분리한다.

약한 패턴:

- 모바일 앱 화면을 차 디스플레이에 그대로 옮긴다.
- 장소 검색, 일정, 메모, 콘텐츠 추천처럼 차량 데이터 없이도 동일하게 동작한다.
- “차 안에서 쓴다”는 사실 외에 차량이어야 할 이유가 없다.
- 차량 데이터는 대시보드에 표시만 하고, 사용자의 다음 행동이나 결과를 바꾸지 않는다.

검증 질문:

1. 차량 밖에서는 얻기 어렵거나 부정확한 정보는 무엇인가?
2. 주행과 정차에서 UI와 기능이 어떻게 달라지는가?
3. 차량이 감지하고 앱이 판단해 행동으로 연결하는 이벤트는 무엇인가?
4. 스마트폰 버전 대비 클릭 수, 정확도, 안전성 또는 자동화가 얼마나 좋아지는가?

### 2.2 창의성

강한 아이디어의 증거:

- “모든 운전자”가 아니라 행동과 상황이 구체적인 한 집단을 먼저 잡는다.
- 문제 발생 전후의 장면, 현재 대안, 대안의 실패 이유가 명확하다.
- 새로운 기술 자체보다 **새로운 문제 정의**, **데이터 조합**, **차량 내 역할 간 경험**에서 차별성이 나온다.
- 한 문장으로 설명할 수 있고, 데모 장면을 본 사람이 가치를 즉시 이해한다.

약한 패턴:

- AI, 안전, 편의 같은 큰 단어만 있고 실제 사용 장면이 없다.
- 여러 사용자와 문제를 한 앱에 모두 넣는다.
- 경쟁 서비스가 있는데 “차량용”이라는 이유만으로 새롭다고 주장한다.
- 아이디어는 독특하지만 빈도·심각도·해결 효과가 약하다.

Pain Point 문장 틀:

> `[타깃]`은 `[이동 상황/트리거]` 때 `[해야 하는 일]`을 하려 하지만, `[현재 대안의 한계]` 때문에 `[시간·비용·불안·안전상의 손실]`을 겪는다.

How Might We 문장 틀:

> 어떻게 하면 `[타깃]`이 `[차량 맥락]`에서 `[차량 데이터/기능]`을 이용해 `[원하는 결과]`를 `[더 안전하게/자동으로/정확하게]` 얻도록 할 수 있을까?

### 2.3 기술 활용성

강한 아이디어의 증거:

- SDK를 기능 목록에 나열하지 않고 **입력 → 판단 → 실행 → 피드백**의 핵심 루프에 배치한다.
- 필요한 API와 권한을 최소화하고, 지원 여부를 capability로 확인하는 대체 흐름을 설계한다.
- 네트워크 단절, 지원하지 않는 차량, 권한 거부 때도 핵심 흐름이 안전하게 종료된다.
- 에뮬레이터에서 어떤 차량 상태를 바꾸고 어떤 앱 반응을 보여줄지 데모 계획이 있다.

약한 패턴:

- 앱의 본체는 일반 웹/모바일 기능이고 마지막 화면에 차량 데이터 하나를 보여준다.
- 아직 제공 여부를 확인하지 않은 API를 핵심 전제로 삼는다.
- 다수의 SDK를 쓰는 것 자체를 기술 우수성으로 설명한다.
- 차량을 직접 제어하면서 권한, 오작동, 사용자 확인 절차를 고려하지 않는다.

핵심 루프 작성 틀:

> `[Vehicle/Navi/Location/STT 이벤트]`를 입력받아 → `[규칙 또는 모델]`로 판단하고 → `[안내/경로/차량 기능/사용자 선택]`을 실행하여 → `[차량 상태 또는 사용자 결과]`로 효과를 확인한다.

### 2.4 사업성

강한 아이디어의 증거:

- 타깃을 차량 보유·이용 패턴까지 구체화한다.
- 한 번 설치할 이유와 매주·매월 다시 사용할 이유가 모두 있다.
- 차량 탑재, 딜러·보험·충전·주차·관광·물류·콘텐츠 등 현실적인 획득 채널을 제시한다.
- 개인정보·안전·권한 비용을 포함해 운영 구조를 설명한다.
- 국내 한 타깃에서 시작해 차종, 지역, B2B/B2C 또는 다른 이동 상황으로 확장하는 순서가 있다.

숫자를 만드는 최소 방식:

```text
예상 MAU = 접근 가능한 대상 차량/사용자 수 × 설치 또는 활성화율 × 월간 사용률
Retention 가설 = 반복 트리거의 월 발생 빈도 × 트리거 발생 시 앱 선택 확률
핵심 효과 = 현재 소요 시간/비용/오류율 - 앱 사용 후 예상값
```

숫자는 과장된 시장 규모보다 **가정의 출처와 계산식**이 중요하다. 초기에는 인터뷰, 관찰, 검색량, 커뮤니티 사례, 유사 서비스 지표로 가정을 표시하고 이후 검증한다.

## 3. Pleos 기술을 아이디어 재료로 쓰기

공식 문서에 제시된 SDK는 다음과 같다. 실제 적용 전에는 최신 버전, 사용 조건, 권한, 에뮬레이터 지원 여부를 다시 확인한다.

| SDK | 활용 가능한 핵심 정보/행동 | 브레인스토밍 질문 |
|---|---|---|
| Vehicle SDK | 차량 상태 조회·제어. Brake, Door, DrivingMode, EV Battery, Fuel, HVAC, Light, Odometer, Safety, Seat, Tire, Window 등 도메인 | 어떤 차량 상태 변화가 사용자의 문제를 미리 알려주거나 자동으로 줄여줄 수 있는가? |
| NaviHelper SDK | 목적지·경유지 설정, 경로 옵션·재탐색, 경로 및 주행 상태 이벤트, 내비게이션 정보 | 목적지까지의 과정에서 “언제·어디서·어떤 순서로” 해야 하는 일을 줄일 수 있는가? |
| FusedLocation SDK | 최근 위치, 위치 업데이트, 지오펜스·근접 알림 | 장소 진입·이탈 순간에만 가치가 생기는 서비스는 무엇인가? |
| SpeechToText SDK | 사용자 음성을 텍스트로 변환 | 운전 중 손과 시선을 쓰지 않고 입력해야 하는 짧은 의도는 무엇인가? |
| TextToSpeech SDK | 텍스트를 차량 오디오로 합성·재생 | 화면을 보지 않아도 이해해야 하는 최소 정보는 무엇인가? |

기술을 많이 쓰는 것이 목표가 아니다. **한두 개 SDK라도 핵심 가치에 깊게 연결**하고 안정적으로 시연하는 편이 낫다.

### 안전·심사 선결 조건

- 앱은 `CarUxRestrictions`를 기준으로 주행 제한 상태를 확인하고 제한 대상 UI·기능을 축소하거나 비활성화해야 한다.
- 주행 중에는 짧게 이해되는 정보, 단순한 메뉴, 큰 터치 영역, 높은 대비, 최소 텍스트를 우선한다.
- 키보드 입력보다 프리셋·최근 항목·음성을 우선하고, 화면을 오래 보거나 반복 조작하게 만들지 않는다.
- 동영상·게임·브라우저 기능은 정차 중에만 사용할 수 있도록 설계하고, 주행 시작 시 중지·숨김 처리한다.
- Vehicle SDK API는 필요한 퍼미션 선언과 사전 승인 범위를 확인해야 한다. 승인되지 않은 퍼미션이나 API 호출은 앱 심사를 통과하지 못할 수 있다.
- capability 확인, 권한 거부, API 미지원, 네트워크 단절, 비동기 호출 실패를 기본 상태로 가정해 안전한 대체 흐름을 만든다.

안전은 별도 장식 항목이 아니라 차량특화성, 기술 활용성, 실제 App Market 탑재 가능성을 동시에 좌우하는 설계 조건이다.

### 차량 이벤트 조합 예시

아래는 아이디어를 만들기 위한 조합법이며 완성 아이디어가 아니다.

```text
사용자 역할 × 이동 단계 × 차량 이벤트 × 외부 맥락 × 원하는 결과
```

- 어린이 동승자 × 장거리 주행 × 좌석/주행 시간 × 휴게 지점 × 멀미·피로 감소
- 전기차 초보 운전자 × 여행 × 배터리/경로 × 충전소 × 충전 불안 감소
- 반려동물 보호자 × 잠시 정차 × 공조/도어 × 외부 온도 × 위험 상태 예방
- 영업·배송 운전자 × 다중 경유 × 경로/정차 × 업무 목록 × 누락·우회 감소
- 초보 운전자 × 주행 종료 × 주행·차량 상태 × 반복 구간 × 학습 가능한 피드백

위 조합은 출발점일 뿐이다. 실제 제안 전에는 API 지원, 안전 정책, 권한 승인 가능성과 기존 서비스 중복을 검증한다.

## 4. 60분 브레인스토밍 진행안

### 1단계 — 타깃과 장면 선택 (5분)

각자 아래 중 하나를 선택하고 더 좁힌다.

- 운전자: 초보, 장거리, 야간, 전기차, 고령, 영업·배송 등
- 동승자: 어린이, 가족, 고령자, 외국인, 반려동물 보호자 등
- 이동 장면: 출퇴근, 여행, 충전, 주차, 픽업, 휴식, 업무, 긴급 상황 등
- 단계: 출발 전 / 주행 / 정차 / 충전·주유 / 주차 / 도착 후

### 2단계 — 문제 장면 수집 (10분)

해결책을 말하지 말고 문제만 한 장면씩 적는다.

```text
누가:
언제/어디서:
무엇을 하려는가:
현재 어떻게 해결하는가:
왜 실패하거나 불편한가:
발생 빈도:
손실(시간/비용/안전/감정):
```

### 3단계 — 차량만의 레버 찾기 (10분)

각 문제에 다음 표시를 한다.

- `[상태]` 차량이 이미 알고 있는 정보
- `[위치·경로]` 목적지와 이동 과정에서 알 수 있는 정보
- `[음성]` 시선·손을 덜 쓰는 입력/출력
- `[제어]` 차량 기능으로 안전하게 실행할 수 있는 행동
- `[전환]` 주행/정차/도착에 따라 달라지는 경험

차량 레버가 하나도 없다면 우선순위를 낮추거나 문제를 다시 정의한다.

### 4단계 — 아이디어 발산 (15분)

문제 하나당 최소 세 가지 해법을 만든다.

- 자동 감지: 사용자가 열기 전에 차량 상태가 먼저 알려준다면?
- 맥락 전환: 주행과 정차에서 다른 경험을 제공한다면?
- 역할 연결: 운전자와 동승자가 서로 다른 화면·행동을 가진다면?
- 예측·예방: 문제가 생긴 후가 아니라 조짐에서 개입한다면?
- 경로 결합: 목적지뿐 아니라 이동 중 해야 할 일을 경로에 녹인다면?
- 피드백 루프: 한 번의 안내가 다음 주행을 개선한다면?
- 오프라인 우선: 네트워크가 없어도 핵심 가치가 유지된다면?

### 5단계 — 평가표로 압축 (10분)

모든 후보를 아래 5점 척도로 평가한다. 한 사람이 밀어붙이지 않도록 먼저 각자 채점한 뒤 평균과 의견 차이를 본다.

### 6단계 — 상위 후보의 데모 장면 작성 (10분)

각 상위 후보는 30초 안에 이해되는 장면을 만든다.

```text
1. 시작 상태: 사용자와 차량은 어떤 상황인가?
2. 트리거: 어떤 차량/경로/위치/음성 이벤트가 발생하는가?
3. 앱 반응: 앱이 무엇을 판단하고 보여주거나 실행하는가?
4. 사용자 행동: 최소 몇 번의 조작이 필요한가?
5. 결과: 무엇이 얼마나 좋아졌는가?
6. 장애 대응: API 미지원·네트워크 단절·권한 거부 시 어떻게 안전하게 끝나는가?
```

## 5. 팀 내부 아이디어 평가표 — 공식 배점 아님

점수 정의:

- **1점:** 주장만 있고 근거·장면이 없음
- **2점:** 일부 설명되지만 일반 모바일 앱과 차이가 약함
- **3점:** 납득 가능한 장면과 구현 경로가 있음
- **4점:** 사용자 근거·차량 연동·반복 사용 구조가 구체적임
- **5점:** 차별성과 효과가 검증 가능하고 데모로 즉시 증명 가능함

| 평가 영역 | 세부 항목 | 점수(1~5) | 근거 또는 보완점 |
|---|---|---:|---|
| 차량특화성 | 스마트폰 대비 차량만의 우위 |  |  |
| 차량특화성 | 주행·정차 맥락 및 차량 기능 결합 |  |  |
| 창의성 | 문제·타깃·Needs의 명확성 |  |  |
| 창의성 | 해결 방식의 독창성과 차별성 |  |  |
| 기술 활용성 | Pleos SDK가 핵심 루프에 필요한 정도 |  |  |
| 기술 활용성 | API·권한·장애 대응의 구체성 |  |  |
| 사업성 | 타깃·유입·MAU 가정의 설득력 |  |  |
| 사업성 | 반복 사용·Retention·확장 가능성 |  |  |
| **합계** | **40점 만점** |  |  |

팀 내부 권장 선별 규칙:

- 합계보다 먼저 **공식 네 평가 영역 중 하나라도 평균 3점 미만인지** 확인한다.
- 차량특화성과 기술 활용성이 약한 후보는 일반 모바일 아이디어일 가능성이 높다.
- 합계가 비슷하면 아래 구현 게이트를 더 많이 통과한 후보를 선택한다.

### 구현 게이트 — Yes/No

- [ ] 현재 공식 문서에서 필요한 SDK/API를 확인했다.
- [ ] 필요한 권한과 승인 가능성을 확인했다.
- [ ] 에뮬레이터로 핵심 차량 이벤트를 재현할 수 있다.
- [ ] 1차 접수 전 최소 프로토타입 또는 화면 녹화를 만들 수 있다.
- [ ] 2차 PT 전 실제 동작 앱으로 완성할 범위다.
- [ ] 주행 중 주의 분산을 줄이는 UX로 설계할 수 있다.
- [ ] 외부 API·데이터가 끊겨도 데모와 핵심 흐름이 완전히 무너지지 않는다.
- [ ] 개인정보·안전·차량 제어 실패 시의 대체 동작이 있다.

## 8. 탈락 가능성이 큰 신호

- “차 안에서도 쓸 수 있다”만 있고 “차라서 더 낫다”가 없다.
- SDK/API가 핵심 가치가 아니라 가산 기능이다.
- 타깃이 모든 운전자 또는 모든 가족처럼 지나치게 넓다.
- 해결할 문제가 여러 개라 핵심 데모 장면을 고를 수 없다.
- MAU는 큰 시장 규모만 제시하고 실제 활성화율·사용 빈도 가정이 없다.
- 실시간 안전 판단처럼 책임이 큰 기능인데 오탐·미탐·실패 대응이 없다.
- 차량 제어 권한이나 capability를 확인하지 않았다.
- 주행 중 긴 텍스트, 다단 메뉴, 키보드 입력, 작은 터치 영역이 필요하다.
- 외부 서버·AI·API가 실패하면 전체 앱이 멈춘다.
- 2차 PT 전 구현 범위를 넘어서며 목업에서도 핵심 가치를 보여주기 어렵다.
- 기능 수는 많지만 30초 안에 설명 가능한 대표 장면이 없다.

## 9. 기획서와 데모에 남겨야 할 증거

아이디어를 선택한 뒤에는 주장보다 증거를 만든다.

| 평가 항목 | 최소 증거 |
|---|---|
| 차량특화성 | 모바일 대비 비교표, 주행/정차별 사용자 흐름, 차량 이벤트 기반 시나리오 |
| 창의성 | 타깃 인터뷰·관찰, 기존 대안 분석, 한 장짜리 Pain Point → Solution 구조 |
| 기술 활용성 | SDK/API 매핑, 에뮬레이터 검증 화면, 입력 → 판단 → 실행 → 피드백 시퀀스 |
| 사업성 | 타깃 규모의 출처, MAU 계산식, 반복 트리거, Retention 가설, 확장 로드맵 |
| 가산점 | 실행 가능한 프로토타입, 짧고 명확한 시연 영상, 소스와 release APK가 포함된 GitHub 저장소 |

공식 FAQ는 접수양식 **5번 개발 계획**에 Pleos Connect 환경의 구현 방식, 주요 개발 범위, SDK/API 사용 계획을 구체적으로 쓰도록 안내한다. 아이디어를 확정하는 순간부터 위 기술 매핑을 함께 작성한다.

### 권장 데모 구조

아래는 공식 형식이 아니라 전달력을 위한 권장 구조다.

1. 문제 장면을 한 문장으로 보여준다.
2. 에뮬레이터에서 차량·경로·위치 상태를 바꾼다.
3. 앱이 이벤트를 받아 핵심 판단과 반응을 수행한다.
4. 사용자는 한두 번의 안전한 조작 또는 음성으로 완료한다.
5. 전후 차이를 시간, 조작 수, 오류 가능성 또는 불안 감소로 보여준다.
6. 네트워크·권한·API 미지원 상황의 안전한 대체 흐름을 짧게 보여준다.
