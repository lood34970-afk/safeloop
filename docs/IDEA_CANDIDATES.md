## 결론

현재는 **1번 운전점수 도우미를 1순위**로 추천한다.

다만 기존 블루링크·기아 커넥트형 운전점수의 단순 복제가 아니라 다음과 같이 재정의해야 한다.

> 출발 준비부터 주행, 도착 후 차량 정리까지 차량과 내비게이션이 확인할 수 있는 근거만 평가하고, 시스템 개입 구간과 센서 신뢰도가 낮은 구간은 제외하며, 다음 이동에서 고칠 습관 하나를 알려주는 **전 주기 운전 습관 코치**

2번 헬스케어 앱은 현재 상태로는 타깃만 있고 Pain Point와 차량만의 해결 방식이 없다. 아래의 **출퇴근 리셋 코치** 정도로 좁히면 후보가 되지만, 차량특화성과 효과 검증은 1번보다 약하다.

## 1. 전 주기 운전 습관 코치

### 한 줄 제안

> 출퇴근 운전자가 탑승 시 짧은 안전 브리핑을 받고, 운전 종료 후 별도 리포트에서 출발 준비·주행·도착 정리 습관을 확인하는 차량 데이터 기반 코치

### 해결하려는 문제

기존 운전점수는 최종 숫자는 보여주지만 다음과 같은 문제가 있다.

- 왜 점수가 떨어졌는지 사용자가 납득하기 어렵다.
- 운전자가 직접 조작한 구간과 크루즈 컨트롤 등 시스템이 개입한 구간이 섞일 수 있다.
- 점수를 확인해도 다음 운전에서 무엇을 바꿔야 할지 명확하지 않다.
- 같은 행동을 반복해도 도로 상황과 센서 신뢰도에 따라 불공정하게 느낄 수 있다.
- 기존 점수는 급가속·과속 등 주행 중 행동에 집중하고, 출발 전 준비와 도착 후 차량 정리 습관은 거의 다루지 않는다.

### 제안 가치

점수 자체보다 다음 네 가지를 차별점으로 잡는다.

1. **전 주기 습관:** 출발 전, 주행 중, 도착 후를 하나의 안전 루틴으로 연결한다.
2. **설명 가능성:** “오늘 72점”이 아니라 어떤 시점의 어떤 행동이 반영됐는지 보여준다.
3. **공정성:** 시스템 개입 구간, 지원하지 않는 센서, 신뢰도가 낮은 이벤트는 평가에서 제외한다.
4. **행동 변화:** 한 주에 한 가지 습관만 선택해 다음 이동에서 개선 여부를 확인한다.

예시:

```text
이번 주 습관: 교차로 진입 전 방향지시등 사용
평가 가능 이벤트: 14회
준수: 11회
평가 제외: 3회 — 내비 이벤트 누락 2회, 센서 미지원 1회
다음 목표: 85% → 90%
```

### 출발 전·주행 중·도착 후 모델

| 단계 | 만들고 싶은 습관 | 확인 가능한 근거 후보 | 피드백 방식 |
|---|---|---|---|
| 출발 전 `Safe Start` | 목적지를 움직이기 전에 설정하고, 열린 도어·트렁크·타이어·차량 경고를 확인한 뒤 출발 | NaviHelper 경로 시작 시점, 차속·기어, Vehicle SDK Door·Tire·Safety | 출발 전 짧은 준비 카드. 이상이 없으면 자동 통과, 이상이 있을 때만 확인 요청 |
| 주행 중 `Safe Drive` | 제한속도 준수, 회전·분기 전 방향지시등 사용, 운전자 직접 조작 구간의 안전 습관 | AAOS 차속, NaviHelper 제한속도·TBT, Vehicle SDK TurnSignal·CruiseControl | 주행 중 점수 화면이나 잦은 경고 없이 데이터만 기록 |
| 도착 후 `Safe Close` | P단·주차브레이크 상태에서 차량 열린 부분과 경고를 확인하고, 다음에 고칠 습관 하나를 선택 | 기어·차속, Vehicle SDK Brake·Door·Window·Light·Safety | 정차가 확인된 후 10초 이내의 종료 카드와 주행 근거 |

핵심 원칙은 **차량 상태 자체를 운전자 잘못으로 채점하지 않는 것**이다. 예를 들어 타이어 경고가 발생한 사실이 벌점이 아니라, 출발 전에 경고를 확인하고 적절한 조치를 선택했는지를 습관으로 본다.

아이·반려동물·귀중품 확인처럼 센서로 증명하기 어려운 항목은 사용자가 선택한 **종료 알림**으로 제공하되 점수에는 넣지 않는다. 앱이 확인할 수 있는 사실과 단순 리마인더를 구분해야 설명 가능한 점수라는 원칙이 유지된다.

안전벨트는 좋은 출발 전 습관이지만 현재 권한과 API 제공 여부가 불확실하므로, 기술 검증 전에는 `Safe Start`의 필수 점수에 포함하지 않는다.

### 평가 항목별 강점

#### 차량특화성

- 실제 차속, 방향지시등, 크루즈 컨트롤 상태, 내비게이션 제한속도·회전 이벤트를 결합한다.
- Door·Tire·Safety·Brake·Window 상태를 이용해 출발과 도착 루틴까지 연결한다.
- 주행 중에는 점수를 노출하지 않고, 정차·도착 후에만 피드백을 제공한다.
- 스마트폰 GPS만 사용하는 서비스보다 차량 신호와 운전자/시스템 개입을 구분할 수 있다.

#### 창의성

단순 점수화는 기존 서비스와 겹치므로 약하다. 다음 요소가 반드시 필요하다.

- 점수 산출 근거와 제외 근거를 함께 표시하는 “신뢰도 있는 점수”
- 출발 전·주행 중·도착 후를 별도 단계로 보여주는 전 주기 안전 루틴
- ADAS/크루즈 개입 구간을 무조건 벌점 처리하지 않는 공정성
- 종합 점수 경쟁보다 개인별 한 가지 습관 개선에 집중
- 차종별 API 지원 차이를 숨기지 않고 평가 가능한 항목만으로 점수 구성

#### 기술 활용성

```text
출발 준비 상태
→ 주행 가능 여부와 확인이 필요한 항목 표시
→ 차량/내비 주행 이벤트
→ 평가 가능한 이벤트인지 판정
→ 운전자 직접 조작 구간만 규칙 적용
→ 도착·주차 상태 확인
→ 단계별 근거와 다음 습관 제안
```

#### 사업성

- 1차 타깃: 주 4일 이상 자가용으로 출퇴근하며 기존 운전점수를 확인하는 20~50대 운전자
- 반복 트리거: 출퇴근마다 탑승 브리핑이 제공되고 주행별 상세 리포트가 누적됨
- 초기 획득: Pleos App Market의 안전·차량관리 카테고리, 차량 출고·정비 접점
- 확장: 초보 운전자 코칭 → 가족 안전 리포트 → 법인차량·플릿 교육 → 보험·안전 캠페인
- 주의: 보험료 할인과 같은 혜택은 제휴가 확정되지 않으면 핵심 가치로 약속하지 않는다.

### 중요한 기술 판단

#### 안전벨트

아이디어에는 매력적이지만 MVP의 필수 항목으로 두지 않는다. Android Automotive의 안전벨트 속성은 존재하나 제3자 앱이 사용할 수 있는 권한인지 불확실하고, 현재 공개된 Vehicle SDK Seat API 목록에서 안전벨트 조회를 확정하지 못했다.

따라서 다음 중 하나를 확인한 뒤에만 추가한다.

- Pleos Vehicle State SDK에 운전석 안전벨트 조회 API가 실제 제공되는가?
- 공모전 참가 앱에 해당 권한이 승인되는가?
- Virtual Console에서 안전벨트 이벤트를 재현할 수 있는가?

#### 깜빡이 없이 차선 변경

방향지시등 상태만으로는 차선 변경 여부를 알 수 없다. “깜빡이를 켰는가”와 “차선을 변경했는가”는 서로 다른 이벤트다.

MVP에서는 다음과 같이 바꾼다.

> 내비게이션이 알려주는 회전·분기 이벤트 주변에서 방향지시등을 사용했는지 평가한다.

실제 차선 변경 평가는 ADAS 차선 변경 이벤트의 사용 가능성과 권한을 확인한 후 확장 기능으로 둔다.

#### ADAS 구간 제외

현재 확실히 확인 가능한 범위에서는 Vehicle SDK의 크루즈 컨트롤 상태를 이용해 **크루즈 활성 구간을 제외**할 수 있다. 이를 “모든 ADAS 사용 구간 제외”로 표현하면 과장이다.

앱의 원칙은 다음과 같이 잡는다.

```text
시스템 개입을 확인할 수 있으면 평가 제외
확인할 수 없으면 제외 여부를 단정하지 않음
데이터가 불충분하면 벌점을 주지 않고 미평가 처리
```

### MVP 범위

#### 포함

1. 출발 전 `Safe Start`: 목적지 사전 설정과 Door·Tire·Safety 상태 확인
2. 주행 세션 시작·종료
3. AAOS 차속과 NaviHelper 제한속도를 비교한 속도 준수율
4. 내비 회전·분기 이벤트와 Vehicle SDK 방향지시등 상태의 시간대 비교
5. Vehicle SDK 크루즈 활성 구간의 평가 제외
6. 도착 후 `Safe Close`: P단·정차 상태에서 Brake·Door·Window 등 확인
7. 출발 전·주행 중·도착 후 근거가 분리된 리포트
8. 다음 이동의 개선 습관 하나 선택

#### 제외

- 안전벨트 점수
- 실제 차선 변경 감지
- 모든 ADAS 상태 판별
- 보험료 할인 또는 외부 보험사 연동
- 운전 중 팝업·경고 남발
- AI 기반 위험운전 판정

### 점수 산식 초안

점수는 이벤트 수가 적거나 데이터가 불완전한 경우 왜곡될 수 있으므로 종합점수와 신뢰도를 함께 표시한다.

```text
출발 준비 완료율 = 완료한 평가 가능 준비 항목 / 평가 가능한 준비 항목
속도 준수율 = 제한속도 이하로 확인된 평가 시간 / 유효한 제한속도·차속이 함께 존재한 시간
방향지시등 준수율 = 방향지시등 사용이 확인된 회전·분기 이벤트 / 평가 가능한 회전·분기 이벤트
도착 정리 완료율 = 완료한 평가 가능 종료 항목 / 평가 가능한 종료 항목

주행 습관 점수 = 속도 준수율 × 0.6 + 방향지시등 준수율 × 0.4
신뢰도 = 평가 가능한 시간·이벤트 수 / 전체 주행 시간·후보 이벤트 수
```

세 단계는 먼저 별도 카드로 보여준다. 하나의 종합점수가 필요하다면 `출발 25% + 주행 50% + 도착 25%`를 초기 가설로 사용할 수 있지만, 위 가중치는 공식 기준이 아니며 사용자 테스트 후 바꿔야 한다. 크루즈 활성 구간, API 미지원 구간, 이벤트 누락 구간은 분모에서 제외한다.

### 데모 시나리오

```text
1. 출발 전 열린 도어 또는 타이어 경고가 있을 때 `Safe Start` 카드가 필요한 확인만 보여준다.
2. 문제를 해소하고 정차 상태에서 내비게이션 경로를 시작한다.
3. Virtual Console에서 차속을 제한속도 이하/이상으로 변경한다.
4. 회전 이벤트 전 방향지시등을 켠 경우와 켜지 않은 경우를 각각 재현한다.
5. 크루즈 컨트롤을 활성화하고 해당 구간이 평가에서 제외되는지 보여준다.
6. P단·주차브레이크 상태로 전환하고 열린 창문이 있는 `Safe Close` 카드를 보여준다.
7. 앱이 출발·주행·도착별 근거, 평가 제외 구간, 다음 습관을 보여준다.
```

### 가장 큰 리스크와 검증 순서

1. `onCurrentRoadSpeedLimit()` 이벤트가 에뮬레이터에서 실제 전달되는지 확인
2. AAOS 차속 접근 권한과 Virtual Console 연동 확인
3. TurnSignal 이벤트와 내비 TBT 이벤트를 동시에 수집할 수 있는지 확인
4. Vehicle SDK 크루즈 상태값과 평가 제외 로직 확인
5. 안전벨트·ADAS SDK는 운영사 문의 후 확장 여부 결정

주행의 네 가지 핵심 신호 중 세 가지 이상과 출발·도착 상태 각 하나 이상이 안정적으로 재현되면 1번 아이디어를 주제로 확정할 수 있다.

## 2. 출퇴근 리셋 코치

### 현재 아이디어의 문제

“출퇴근 차량 이용자를 위한 헬스케어”는 아직 다음이 정해지지 않았다.

- 어떤 건강 문제인지: 피로, 스트레스, 자세, 운동 부족, 수면, 멀미 등
- 운전 중인지, 출발 전인지, 도착 후인지
- 차량 데이터가 어떤 판단을 바꾸는지
- 효과를 무엇으로 측정할지
- 일반 스마트폰 헬스케어 앱보다 나은 이유가 무엇인지

### 좁힌 제안

> 40분 이상 출퇴근하는 직장인이 도착 직후 그대로 업무나 휴식으로 넘어가며 피로가 누적되는 문제를, 실제 연속 주행 시간과 도착·주차 상태를 이용해 2분짜리 회복 루틴으로 연결하는 앱

의료 진단 앱이 아니라 **출퇴근 전후의 작은 행동을 만드는 웰니스 앱**으로 정의한다.

### 사용자 흐름

```text
출발
→ 실제 연속 주행 시간과 예상 도착시간 확인
→ 주행 중 시각적 상호작용 없음
→ 장시간 주행 후 P단·도착 확인
→ 2분 목·어깨·호흡 회복 루틴 제안
→ 수행 여부와 주관적 피로도 1회 입력
→ 출퇴근 패턴별 실천율과 체감 변화 제공
```

### 차량특화 포인트

- 스마트폰의 단순 시간 알림이 아니라 실제 주행 세션과 도착 상태를 트리거로 사용한다.
- NaviHelper의 목적지·남은 시간과 Vehicle/AAOS의 주행·주차 상태를 결합한다.
- 주행 중에는 아무 조작도 요구하지 않고 도착 직후에만 루틴을 제공한다.
- 장거리 통근일과 짧은 통근일에 루틴 강도를 다르게 한다.

### 기술 후보

| 기능 | 데이터/API | 비고 |
|---|---|---|
| 출퇴근 세션 판별 | NaviHelper 목적지·주행 상태, 시간대, 로컬 기록 | 집/직장 저장은 개인정보 최소화 필요 |
| 연속 주행 시간 | NaviHelper Trip 정보 또는 로컬 세션 타이머 | 백그라운드 복원 검증 필요 |
| 정차·도착 확인 | NaviHelper 도착 이벤트, AAOS 기어/속도 | P단·0km/h 등 복수 조건 권장 |
| 루틴 안내 | 정차 후 Compose UI | 주행 중 UI 비활성화 |
| 음성 안내 | TextToSpeech | 현재 SDK 사용 상태가 준비 중이므로 선택 기능 |
| 건강 데이터 연동 | Health Connect·웨어러블 | 개인정보·권한·개발량 때문에 MVP 제외 권장 |

### MVP 범위

1. 출퇴근 목적지와 시간대 설정
2. 실제 연속 주행시간 기록
3. 40분 이상 주행하고 도착·주차했을 때만 2분 루틴 제안
4. 루틴 완료 여부와 피로도 1~5 입력
5. 주간 실천율과 피로도 변화 표시

### 약점

- 차량 밖 스마트폰 앱도 위치와 활동 인식으로 비슷한 기능을 만들 수 있다.
- 피로 개선 효과를 단기간에 증명하기 어렵다.
- 헬스케어라는 표현이 의료적 효능 주장으로 확대되면 검증·책임 부담이 커진다.
- 주행 중 피로 감지나 생체 신호 측정까지 넓히면 지원 센서와 권한이 부족하다.

### 강화 방법

- “건강 전반” 대신 “장시간 출퇴근 후 목·어깨 피로와 루틴 실천” 하나만 해결한다.
- 실제 통근자 5명에게 문제 인터뷰를 하고 현재 대안과 실패 이유를 확보한다.
- 차량이 정확히 감지하는 도착 순간을 핵심 가치로 삼는다.
- 건강 효과보다 **실천율**, **루틴 완료율**, **주관적 피로도 변화**를 초기 지표로 사용한다.

## 두 아이디어를 결합할 경우

두 앱을 처음부터 합치는 것은 권장하지 않는다. 안전운전과 웰니스가 한 앱 안에서 경쟁하면 메시지가 흐려지고 구현 범위가 커진다.

다만 1번을 주제로 선택한 뒤 다음처럼 제한적인 웰니스 기능을 확장 로드맵에 둘 수 있다.

> 장시간 주행이 종료되면 운전점수와 별개로 2분 회복 루틴을 제안한다.

이 기능은 사업 확장 설명에는 도움이 되지만 1차 MVP에는 넣지 않는다.

## 다음 의사결정

### 1번 확정 조건

- [ ] AAOS 차속을 에뮬레이터에서 읽을 수 있다.
- [ ] NaviHelper 제한속도 이벤트를 받을 수 있다.
- [ ] Vehicle SDK 방향지시등 상태를 받을 수 있다.
- [ ] 크루즈 컨트롤 활성 상태를 확인할 수 있다.
- [ ] 위 이벤트를 시간축에 저장하고 도착 후 근거 화면으로 재생할 수 있다.

### 2번을 계속 검토할 조건

- [ ] 장시간 차량 출퇴근자 5명 중 3명 이상이 도착 후 피로 전환 문제를 반복적으로 겪는다.
- [ ] 기존 스마트폰 알림이나 스트레칭 앱을 쓰지 않는 이유가 확인된다.
- [ ] 차량의 도착·주차 트리거가 실천율을 높인다는 가설을 테스트할 수 있다.

### 추천 작업 순서

1. 1번의 네 핵심 API를 각각 최소 코드로 검증한다.
2. 동시에 통근 운전자 5명에게 기존 운전점수의 불만과 실제 개선 행동을 인터뷰한다.
3. API 검증이 성공하면 1번의 리포트 화면과 데모 시나리오를 제작한다.
4. 핵심 API가 두 개 이상 막히면 2-A 또는 다른 차량특화 아이디어로 전환한다.
