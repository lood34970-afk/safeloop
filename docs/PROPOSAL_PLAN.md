# 전 주기 운전 습관 코치 제안서 작성 계획

> **기준일:** 2026-10-28 (KST)  
> **공식 양식:** [contest-application-consent.official.docx](contest-application-consent.official.docx)  
> **접수 마감:** 2026-11-15 23:59

## 결론

현재 스타터 프로젝트로 앱 개발을 시작할 수 있다. 2026-10-28에 JDK 17을 지정한 상태에서 `assembleDebug` 빌드가 성공했다.

다만 최초 아이디어의 모든 항목이 모든 차량에서 동일하게 제공된다는 의미는 아니다. 안전벨트·실제 차선 변경·ADAS 개입 판별도 기술 검증 범위에 포함하되, 실제 API·권한·차량 capability에 따라 `평가`, `대체 감지`, `미평가` 중 하나로 명확히 처리한다.

개발보다 제안서를 먼저 잡는 것이 맞지만, 제안서를 완전히 끝낸 뒤 개발을 시작하지는 않는다. 다음 순서로 진행한다.

1. 공식 양식 1~6번의 1차 초안을 작성한다.
2. 제안서의 핵심 주장을 좌우하는 API를 최소 코드로 검증한다.
3. 실제 확인된 API만으로 기능 범위와 개발 계획을 확정한다.
4. 핵심 화면 목업과 짧은 동작 프로토타입을 만든다.
5. 이를 제안서 7번 참고자료에 연결해 가산점을 노린다.

## 현재 개발 가능 범위

현재 프로젝트에는 Vehicle SDK 2.3.2와 NaviHelper 3.0.5, 진단에 필요한 최소 차량 퍼미션이 포함되어 있다. ADAS SDK는 문서와 AVD 서비스는 확인했지만 공개 Maven 아티팩트가 확인되지 않아 배포 좌표와 권한을 운영사에 문의해야 한다.

## 주제 경쟁력 판단

### 좋은 점

- 차량 상태와 내비게이션을 함께 써야 하므로 차량특화성이 강하다.
- 출발 전, 주행 중, 도착 후를 연결하면 기존의 주행점수 앱과 구분된다.
- 출퇴근마다 반복되어 Retention을 설명하기 쉽다.
- Virtual Console에서 차량 상태가 바뀔 때 앱 반응을 시연하기 좋다.
- 안전운전, 초보 운전자, 가족, 법인차량 등 확장 방향이 명확하다.

### 그대로 제출하면 약한 점

- “운전점수”만 강조하면 블루링크·기아 커넥트·보험사 점수의 복제로 보일 수 있다.
- 많은 기능을 약속하면 실제 API 권한과 에뮬레이터 지원 범위에서 막힐 수 있다.
- 단일 종합점수는 운전자가 왜 감점됐는지 이해하기 어렵고 불공정하게 느낄 수 있다.
- 타이어 경고나 차량 이상처럼 운전자 책임이 아닌 상태를 감점하면 서비스 신뢰도가 떨어진다.
- 보험 할인이나 사고 감소 효과는 제휴·장기 데이터 없이 증명하기 어렵다.

### 제안서에서 강조할 차별점

1. **전 주기:** 출발 준비 `Safe Start`, 주행 `Safe Drive`, 도착 정리 `Safe Close`를 연결한다.
2. **설명 가능성:** 점수와 함께 반영된 사건, 제외된 사건, 제외 이유를 보여준다.
3. **공정성:** 크루즈 활성, API 미지원, 신뢰도 부족 구간은 벌점이 아니라 미평가 처리한다.
4. **행동 변화:** 전체 점수 경쟁보다 다음 이동에서 개선할 습관 하나를 제시한다.
5. **최소 개입:** 주행 중에는 데이터를 기록하고, 피드백은 출발 전이나 도착 후에만 제공한다.

앱을 다음 문장으로 정의한다.

> 차량과 내비게이션이 확인할 수 있는 근거로 출발 준비, 주행, 도착 정리 습관을 기록하고, 탑승 시 짧은 안전 브리핑과 운전 종료 후 별도 리포트를 제공하는 전 주기 안전운전 코치

## 공식 제안서 항목

공식 DOCX에서 확인한 작품 소개 항목은 다음 8개다. 소개 자료의 분량 제한은 없으며, 여러 줄 입력란은 내용에 따라 늘어난다.

### 1 앱 한 줄 소개

앱을 한 문장으로 소개하는 항목이다.

초안:

> 운전자의 출발 준비부터 주행, 도착 후 차량 정리까지 차량 데이터로 확인하고 다음 이동에서 개선할 안전 습관 하나를 제안하는 설명 가능한 운전 코치

### 2 기획 배경

작성할 내용:

- 기존 운전점수는 급가속·과속 같은 주행 중 행동과 결과 숫자에 집중한다.
- 초기 인터뷰에서는 위반 사항을 통해 점수 이유를 이해했지만, 일부는 보험 할인 혜택이 있을 때만 행동을 바꿨다.
- 문제의 초점은 점수 설명 부족보다 행동을 꾸준히 이어갈 동기와 운전 전후 습관 누락에 있다.
- 출발 전 차량 상태 확인과 도착 후 차량 정리는 중요한 안전 습관이지만 기존 점수에서 빠져 있다.
- 시스템 개입이나 센서 미지원 구간까지 같은 기준으로 평가하면 신뢰도가 떨어진다.
- 매일 반복되는 출퇴근을 안전 습관 형성의 계기로 바꿀 필요가 있다.

필요한 근거:

- 기존 운전점수 사용자 5명 이상 인터뷰
- 점수를 확인한 뒤 실제 행동을 바꾼 경험과 바꾸지 못한 이유
- 출발 전·도착 후 자주 놓치는 행동 사례
- 기존 서비스 비교표

### 3 앱 주요 기능 및 차량 특화 요소

구성:

- `Safe Start`: 목적지 사전 설정, Door·Tire·Safety 기반 출발 준비
- `Safe Drive`: 차속·제한속도, 방향지시등·회전 이벤트, 크루즈 구간 제외
- `Safe Close`: 정차·P단·주차브레이크 확인 후 열린 차량 요소 확인
- 탑승 시 출발 상태와 이어갈 행동 하나를 보여 주는 짧은 브리핑
- 운전 종료 후 단계별 근거와 데이터 신뢰도를 보여 주는 별도 리포트

차량 특화 설명:

- 스마트폰 GPS가 아니라 차량 차속·방향지시등·브레이크·도어 등 실제 차량 상태를 사용한다.
- 주행·정차 상태에 따라 앱의 동작과 UI를 다르게 한다.
- NaviHelper의 경로·제한속도·회전 이벤트를 차량 상태와 결합한다.
- 지원하지 않는 capability는 감점하지 않고 해당 평가를 제외한다.

### 4 주요 사용 시나리오

대표 시나리오:

1. 출근 전 운전자가 차량에 탑승한다.
2. 탑승 브리핑이 열린 도어 또는 타이어 경고와 이어서 실천할 행동 하나만 짧게 보여준다.
3. 운전자는 정차 상태에서 목적지를 설정하고 출발한다.
4. 앱은 주행 중 화면 조작을 요구하지 않고 차속, 제한속도, 회전 이벤트, 방향지시등, 크루즈 상태를 기록한다.
5. 크루즈 활성 또는 데이터가 불충분한 구간은 미평가 처리한다.
6. 도착해 P단과 주차브레이크가 확인되면 `Safe Close`가 열린 창문·도어 등을 알려준다.
7. 운전 종료 후 별도 리포트에서 출발·주행·도착별 근거와 다음에 개선할 습관 하나를 보여준다.

### 5 개발 계획

공식 FAQ에서 특히 구체적으로 작성하도록 안내한 항목이다.

작성할 내용:

- Android Automotive 기반 Kotlin·Compose 앱
- Vehicle SDK 2.3.2의 Door, Tire, Safety, TurnSignal, DrivingMode, Brake, Window 사용 계획
- NaviHelper의 경로 상태, TBT, 현재 도로 제한속도 이벤트 사용 계획
- AAOS `CarPropertyManager`의 차속·기어 사용 계획
- capability와 권한 확인 후 지원 항목만 활성화하는 구조
- 이벤트를 시간축으로 기록하는 로컬 저장 구조
- 주행 중 UI 제한과 `CarUxRestrictions` 대응
- 네트워크·API 미지원·권한 거부 시 미평가 처리
- Pleos Connect Emulator와 Virtual Console을 이용한 상태별 테스트

개발 범위:

```text
1차 접수 전: 핵심 API 검증 + 주요 화면 목업 + 가능하면 동작 프로토타입
2차 PT 전: Safe Start·Safe Drive·Safe Close 핵심 시나리오 완성
전시 준비: 오류 수정, APK 안정화, 시연 영상 제작
```

### 6 기대효과 및 발전 가능성

1차 타깃:

- 주 4일 이상 자가용으로 출퇴근하는 운전자
- 기존 운전점수를 이해하지만 행동을 꾸준히 유지할 동기가 필요한 사용자
- 안전 습관을 만들고 싶은 초보 운전자

핵심 지표:

- 출발·도착 루틴 완료율
- 평가 가능한 회전 이벤트의 방향지시등 준수율
- 제한속도 준수 시간 비율
- 탑승 브리핑 확인율과 운전 종료 후 상세 리포트 열람률
- 4주 후 Retention
- 선택한 습관의 최근 주행 대비 개선율

확장 순서:

```text
개인 출퇴근 운전자
→ 초보 운전자와 가족 안전 코칭
→ 법인차량·플릿 운전자 교육
→ 정비·보험·안전 캠페인 제휴
```

MAU와 Retention은 근거 없는 큰 숫자를 쓰지 않고, 타깃 차량 수 × 설치율 × 월간 사용률의 가정을 표시한다.

### 7 참고자료 선택 가산점

제출 후보:

- 앱 화면 목업
- Virtual Console에서 차량 상태를 변경하는 시연 영상
- GitHub 저장소
- 소스 코드와 release APK
- 차량 이벤트 → 판단 → 리포트 흐름도

1차 접수 때 완성 앱은 필수가 아니지만, 화면 녹화·목업·프로토타입도 인정되며 개발 산출물 수준에 따라 가산점이 있다.

### 8 숏폼 링크 선택 가산점 없음

본상과 별도인 숏폼 특별상 참가 항목이다. 본상 가산점은 없으므로 핵심 제안서와 프로토타입을 우선한다.

핵심 기능이 막히면 제안서에서 기능을 과장하지 말고 다음처럼 축소한다.

- 실제 차선 변경 → 내비 회전·분기 전 방향지시등
- 모든 ADAS 제외 → 확인 가능한 크루즈 활성 구간 제외
- 안전벨트 점수 → API·권한을 실제로 시도하고, 미지원 환경에서는 미평가
- 차량 제어 → 차량 상태 조회와 운전자 확인 중심

## 제출 운영 주의사항

- 공식 양식이 곧 필수 기획서다.
- 작품 소개에는 참가자 성명, 연락처, 이메일, 소속을 적지 않는다.
- 개인정보는 참가신청서와 동의서에만 작성한다.
- 팀 참가 시 대표자와 모든 팀원이 각각 동의·서명하고 제출 메일에 전원을 CC한다.
- 수정 제출 시 기존 파일을 포함한 전체 제출물과 서명 완료 동의서를 다시 보낸다.
- 모든 출품 자료는 순수 창작물이어야 하며 타 공모전 수상작·제3자 권리 침해 자료를 사용할 수 없다.
- 1차 합격 20팀은 2차 오프라인 PT에서 실제 동작 앱을 필수 시연한다.
